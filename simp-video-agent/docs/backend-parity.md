# 两条导出后端的实测对比（canvas vs chrome）

这份文件记录的是**量出来的数**，不是判断。结论在最后一节。

工具（都需要 `danger-full-access`，因为要拉 Chrome）：

```powershell
node packages/agent-tools/dist/verify-backends.mjs --at 0.2,0.6,0.9   # 整条管线 + 逐像素对比
node packages/agent-tools/dist/diag-backends.mjs                      # 按镜头类型拆差异来源
node packages/agent-tools/dist/diag-text-metrics.mjs                  # 文字度量跨后端对比（决定性）
node packages/agent-tools/dist/diag-text-offset.mjs                   # 是否存在亚像素位置偏移
```

两条路都实现 `ExportBackend`：

| 后端 | 怎么渲染 | 依赖 | 实测耗时（320×180，1s，30 帧） |
|---|---|---|---|
| `canvas`（默认） | `@napi-rs/canvas` 逐帧直接画 | 无浏览器 | ~0.7–1.1s |
| `chrome` | 逐帧拉 `preview.html` 截图 | Chrome（命名管道 → 需 danger-full-access） | ~4.1–4.6s（慢 4–6×） |

---

## 1. 差异按镜头类型拆开

`verify-backends.mjs`（跑完整条管线：提交作业 → 渲染 → ffmpeg 编码 → ffprobe 回读 → 抽帧对比），
320×180 / 1s / 30fps，t=0.2 与 t=0.9：

| 镜头 | 平均 \|Δ\|（最差） | 峰值 \|Δ\| | 判据 |
|---|---|---|---|
| 纯几何（无发光无文字） | 0.406 | 63 | 像素级差异，无结构分叉 ✅ |
| 几何 + 发光 0.6 | 0.674 | 47 | 像素级差异，无结构分叉 ✅ |
| 几何 + 文字（中文 + 拉丁） | 7.106 | 254 | 栅格化级别差异 ✅ |

`diag-backends.mjs` 在同一时刻做单帧对比，能看到更干净的分档：

| 镜头 | 差异像素% | 平均 \|Δ\| | 峰值 \|Δ\| |
|---|---|---|---|
| 纯曲线 glow=0（t=0.1，不透明度约 0.12） | 1.22% | **0.010** | **2** |
| 纯曲线 glow=0.6 | 15.77% | 0.166 | 4 |
| 纯中文大字（48px） | 4.23% | 7.721 | 244 |
| 纯拉丁大字（48px） | 7.01% | 10.607 | 244 |

三档差异各自的原因：

- **几何**：同一份 `evaluate` + `paintScene` + 同一个矩阵。差在折线的抗锯齿与微段连接。
  ⚠️ 一个反直觉的实测结论：**采样密度会放大差异**。曲线在 840 像素里放了 800 个点，
  微段的连接方式在两条栅格化器上不同，所以"纯几何"的峰值也能到 63；
  把时刻挪到不透明度只有 0.12 时（暗曲线）峰值掉到 2。
  这也说明**峰值不能当判据**。
- **发光**：`shadowBlur` 是 Canvas2D 里最依赖实现的一块 —— 两边都画得出光晕，
  但羽化半径与衰减曲线不同。幅度小（峰值 4~47），面积大（差异像素占比高）。
- **文字**：峰值 244~254 最吓人，但已被证明不是字体或位置问题（见下面两节）。

## 2. 文字：先证明"是不是同一个字体"

`diag-text-metrics.mjs`：同一族名、同一字号，在两条路里各测 `measureText`。

| 文字 | canvas 宽度 | chrome 宽度 | 差 |
|---|---|---|---|
| 正弦曲线 sin(x) @48 | 324.05 | 324.05 | **0.00px** |
| sin ABC 123 @48 | 270.35 | 270.35 | **0.00px** |
| 信号采样 @32 | 128.00 | 128.00 | **0.00px** |

Chrome 侧 `document.fonts.check` 两个族都返回 `true`。
**度量完全一致 ⇒ 两条路用的是同一个字体文件、同一套字形宽度。**

## 3. 文字：再排除"是不是位置错开了半像素"

`diag-text-offset.mjs`：把 canvas 那帧按 (dx,dy) 重采样后与 chrome 帧比，找最小值。

```
            dx=-1  dx=-0.5     dx=0   dx=0.5     dx=1
dy=0       15.949   15.432   15.210   15.482   16.024
最佳偏移 = (0,-1) → 14.551（相对无偏移只降 4.3%）
```

真正的半像素错位应当把差异**降 90% 以上**（边缘像素会几乎完全重合）。
只降 4.3% ⇒ **没有位置偏移**。

## 4. 结论

> 两条后端画的是**同一个东西**：同一份 `evaluate` + `paintScene`、同一个字体、
> 同一套文字度量、同一个位置、同样的矩阵。剩下的差异是**栅格化**。
>
> 判据因此不能拿"峰值"说事 —— 一条抗锯齿边缘一边取 60、一边取 255 就是 195，
> 一个像素就能把峰值顶到 200+。判"有没有结构分叉"要看**平均 |Δ|**：
> 真正的代码级分叉（换了矩阵、求值不同、对象位移）会表现为平均差**几十到上百**，
> 而三档实测分别是 0.406 / 0.674 / 7.106。
>
> `verify-backends.mjs` 的门槛就是按这个量级定的，并且把数字与归因一起打出来，
> 以免下一个人又把文字峰值误读成故障。

## 4.5 控制臂：链路零噪声（实测，不是假设）

上面所有归因都依赖一个前提：[提交作业 → 渲染 → ffmpeg 编码 → 抽帧 → 解码]
这条链路本身没有引入差异。这个前提**做过了**：

```
=== 控制臂：canvas 自比对（同一文档导出两次）===
  t=0.2  差异像素 0.00%  平均 |Δ| 0.000  峰值 0
  t=0.9  差异像素 0.00%  平均 |Δ| 0.000  峰值 0
```

同一份文档、同一个后端（canvas）导出两次，抽帧后**逐字节相同**。
所以第 1 节表格里的每一个数都是真实的渲染器差异，不需要扣任何噪声。
`verify-backends.mjs` 把这一臂做成了硬门槛（自比对不为 0 直接失败）。

## 5. 这条对比顺带挖出来的一个真问题（已修）

做对比之前，headless 那条路**从来没有注册过自托管字体**：
`paintScene` 用的族名是 `SvaInter, SvaNotoCJK, sans-serif`，浏览器那条路有
`@font-face` + `document.fonts.load` 把它们加载起来 —— 而 `@napi-rs/canvas`
这一侧一路回退到了系统字体。

实测证据（48px 下"正弦"的测量宽度）：

| 状态 | 中文宽度 | 每字 |
|---|---|---|
| 未注册字体 | 48.00px | 24px（回退字形） |
| 注册之后 | 96.00px | 48px（真字形） |

中文那格 canvas 出图从 796 字节涨到 3335 字节 —— 之前画的是回退字形。
这违反项目铁律"落到系统 sans-serif 就等于把确定性交给了机器"。

修法：`engine-node/src/render.ts` 新增 `registerHeadlessFonts()`，
`renderFrames()` 首次调用时自动注册，**字体缺失直接报错**（而不是悄悄换字体）。
`assertFontsRegistered()` 供调用方在更早的位置检查。

## 6. 已知残留差异（不修，但要知情）

- `glow`（`shadowBlur`）的羽化算法两边不同：幅度极小（峰值 4），但面积大。
  若将来要求"两条后端逐字节相同"，这一项和文字抗锯齿就是全部障碍 ——
  而那样的代价是放弃其中一条后端。
- Chrome 侧开了 `--font-render-hinting=none --disable-lcd-text`，
  所以它做的抗锯齿与 canvas 默认的抗锯齿仍然不是同一套实现。
  这一点无法通过参数抹平，除非改用同一套栅格化器。
