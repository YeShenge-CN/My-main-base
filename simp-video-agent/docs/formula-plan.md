# 公式（KaTeX 那条路）的方案对照 —— 需要你拍板

> 服务对象：规范 §3 要求的「公式」。现在**没有任何公式排版** —— 文字一律是 canvas fillText 画的一行行美术字。
> （第二十轮补了 SvaMath（Noto Sans Math），所以希腊字母与 ∑ ∫ √ ≤ ≠ 这类**符号**已经能画了 ——
>  差的不是字形，是**排版**。）

## 先说三条硬约束（它们决定哪个方案可行）

1. **evaluate(doc,t) 是纯函数**：不碰 DOM、不读时钟、不取随机数（铁律 1）。
2. **两条渲染路径必须给出同一份画面**（canvas 默认快、Chrome 保真慢）——
   「预览 = 成片」是这个项目的硬约束，已由像素级测试与后端一致性门限守着。
3. **canvas 是默认导出后端**，不需要浏览器、快十倍；Chrome 那条路要 danger-full-access。

## 四个方案

| | 做法 | 与三条约束的关系 | 代价 |
|---|---|---|---|
| **A 自研排版（大而全）** | 在 engine-core 里实现 TeX 的盒模型（基线/深度/上下标/分数/根号/大运算符） | ✅ 全相容（排版是纯函数，画笔只按位置画） | TeX 排版是深水区；**度量精度**是命门（我们没有 TFM 数据） |
| **B 物化 KaTeX 的几何** | 构建期/写入期用 KaTeX 把公式渲染成**矢量路径**，几何存进文档，两条后端都画同一份 path | ⚠️ 破坏「文档只有一种写路径」：几何要么由渲染器生成（引擎依赖渲染依赖），要么由调用方塞进来；文档也会变大 | 公式质量 = 真 TeX；但要引入 KaTeX（+ 其字体，或转路径后不再需要字体） |
| **C 走 DOM** | 预览把公式当 HTML 叠在 canvas 上；导出只能靠 Chrome 截图 | ❌ 与约束 2、3 直接冲突：canvas 后端对公式无能为力 → 「有公式的文档只能用 Chrome 导出」 | 实现最省事，但**产物不再是确定性的**（浏览器版本/字体都会影响） |
| **D 自研排版（小范围）** | 只做最常用的四类：**上下标 / 分数 / 根号 / 希腊字母与运算符**；盒模型用 **em 网格**（每个字形按 1em 估宽、上下标 0.7em 缩放），不追求真 TeX 的字距 | ✅ 全相容，而且**因为只用 em 网格，度量不确定性被彻底绕开** | 不如真 TeX 漂亮（可能略松/略紧）；复杂公式（矩阵、多行对齐）明确不做 |

## 我的推荐：**D**，理由与边界

- 它与三条硬约束**同时**相容，不需要「有公式就只能慢十倍」这种妥协；
- **可以增量长大**：先做上下标 + 分数 + 根号（这三样覆盖中学与科普视频的绝大多数公式），
  真实任务里不够用再加（这正是这个项目一贯的做法：不过度工程，等证据）；
- **em 网格**是关键取舍：它让「排版」只依赖我们自己定义的网格，而不是字体度量 ——
  于是两条后端不可能分叉（这是 B 方案里最容易出问题的地方）。

**如果你要「出版级公式」**（真 TeX 的字距与断行），那只能在 B 与 C 里选：
- 选 B（物化几何）：质量最高，但要接受「文档里躺着渲染产物」以及一个写入期的新依赖；
- 选 C（DOM + Chrome 导出）：实现最快，但要接受「**有公式就不能用 canvas 导出**」，
  等于放弃约束 3 —— 这一条影响「导出速度」与「无浏览器环境能不能出片」。

## 需要你回答的三个问题

1. **目标是什么档**：科普级（D 够用）还是出版级（必须 B 或 C）？
2. 若选 D：**第一批做哪几个构造**？我建议 x^{上标}、x_{下标}、分数、根号。
3. 若选 B：**几何什么时候生成、由谁生成**？这决定了它是不是能守住「唯一写路径」。
   （我倾向：写入时由引擎生成并落盘 —— 但那意味着引擎要依赖 KaTeX，是架构级改动。）

## 在此之前不需要拍板的部分（现在就能做）

- **行内数学的「美术字」**：有了 SvaMath，y = sin(x)、2π、∑ 这类**已经是可用的**
  （第二十轮实测：真调模型写 π 已经能正确显示）；
- **上标/下标**这一档的排版（如果只做上下标，D 的复杂度很低，可以先落地看看手感）。
